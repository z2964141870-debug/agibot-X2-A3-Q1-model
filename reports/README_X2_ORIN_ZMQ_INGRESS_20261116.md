# X2 Orin 人体输入双通道 ZMQ 回环

## Done

在 SoC1 用原 CPU ONNX 策略、保存的 `orin_real_worn` 人体数据和固定合成反馈，做了共享 REP、独立 REP、独立 REP、共享 REP 四轮。每轮 180 个人体请求和 300 个状态请求，按约 30/50 Hz 计划释放。两个客户端均只允许一个未完成请求。每轮使用本机随机 TCP 回环端口。四个源码及输入录制大小和内容以 SHA-256 校验。板端退出状态 0，结果原件与 Mac 同 SHA-256。

独立方案接收人体数据与运行策略的线程分开，只在人体缓冲区更新或抽窗时共享短锁。每次就绪核对 10 个参考槽的最右支持帧已在真实取窗截止前入库。四轮各 289 个就绪状态，未就绪均出现在暖窗阶段，总计每轮 11 个。配对两组中，共同就绪周期均为 289，参考槽时刻和支持同时一致的分别是 284 和 287。所有轮的连续目标跳变峰值均为 9.37°。

| 指标，分别列两轮 | 共享 REP | 独立 REP |
| --- | ---: | ---: |
| 人体发送到服务接收 P95 | 7.01 / 7.42 ms | 1.22 / 1.74 ms |
| 人体发送到收到确认 P95 | 7.59 / 8.25 ms | 3.18 / 2.96 ms |
| 状态发送到收到回复 P95 | 12.39 / 12.78 ms | 13.69 / 13.29 ms |
| 状态超过 20 ms，共 300 次/轮 | 0 / 1 | 0 / 2 |
| 状态最大往返 | 17.08 / 22.00 ms | 18.22 / 29.55 ms |

双 REP 确实缩短人体确认等待，但本轮状态 RPC 的 P95 小幅上升，最慢一次为 29.55 ms。人体确认提前会改变少量周期可见的源参考。当前不换部署入口。短轮回环缺真实 FGP 并发、BLE、真实机器人反馈及电机输出。后续需用更长录制把状态端从接收、取窗、ONNX 前向到回包分别计时，再做板端负载对照。板端原件位于 `/tmp/x2-zmq-ingress.5ldJSq/result.json`。
