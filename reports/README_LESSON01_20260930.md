## 本节只解决一个问题

从“衣服已经输出 SMPL”到“机器人能稳定抬手”，中间的策略到底做什么，训练又改了什么。

学完本节应能区分：人体参考、机器人反馈、策略输出、PD 力矩，以及参数更新。暂时不要求推导 PPO 的损失公式。

## 1. 先区分两种模型

| 名称 | 描述什么 | 本轮主要训练它吗 |
| --- | --- | --- |
| 机器人资产模型，例如 URDF / MJCF / USD | 连杆、关节、质量、惯量、碰撞体和执行器等物理描述 | 首先核实它是否正确，不靠 PPO 自动修改这些描述 |
| 策略模型，例如一个神经网络 | 输入机器人观测与任务参考，输出控制动作 | 是；PPO 主要更新网络参数，也会训练辅助估计回报的 critic |

checkpoint 可以同时保存策略、critic、优化器和归一化信息；导出给部署的模型未必包含这些全部内容。

你已经完成的 FGP/SMPL 是人体感知和动作表示链路。机器人策略要解决的是：在自身状态、动力学和接触约束下，怎样实现希望的动作。

## 2. 用一次抬手串起控制循环

假设你希望右臂抬高。SMPL 提供人体姿态，再经选定接口成为动作参考。机器人还要读取自己的实际关节角、角速度、机身朝向等反馈。

同样的抬手目标，在机器人身体直立和已经前倾时，合理的控制可能不同。所以策略通常要同时看参考和机器人反馈。

```text
人体动作 → 参考 ───────────┐
                         ↓
机器人实际反馈 → 观测 → 策略网络 → action → 关节目标 → PD → 力矩
      ↑                                                      ↓
      └──────────────── 仿真物理或真实机器人 ←─────────────────┘
```

这叫闭环：根据实际发生的运动，继续决定下一次命令。前向推理使用网络参数；不意味着每次控制都在修改网络参数。

## 3. 三个容易混淆的量

- **参考动作**：希望机器人完成什么任务或跟踪什么运动。
- **策略输出 action**：网络对“现在怎样控制”的回答；它的单位和解释由具体代码决定。
- **实际关节角**：传感器反馈或仿真状态里，关节目前真正处于的位置。

已核对的 X2 评估程序把 action 解释为默认姿态附近的位置偏移。概念上是：

```python
# 教学伪代码；不连接机器人
action = policy(robot_observation, motion_reference)
joint_target = default_joint_angle + action_scale * action
torque = kp * (joint_target - actual_angle) - kd * actual_velocity
```

这里目标速度取零。`kp` 根据位置差产生纠正作用，`kd` 对运动提供阻尼。代码使用弧度；交互例子显示角度，计算时转换为弧度。真实运行还可能有限位、滤波、力矩饱和和前馈项。

**网络发出 20° 的目标，不等于机器人已经到达 20°。** 电机产生力矩后，实际运动还受惯性、重力和接触影响。

## 4. 在交互例子里做两次观察

例子是“单个时刻的 PD 计算”，没有推进物理仿真，也没有训练网络。你手动改变实际角只是在比较不同反馈状态，不代表真实关节可以瞬间跳过去。参数仅用于教学，不是 X2/A3/Q1 的控制参数。

1. 实际角与角速度都保持 0，只改变目标角：观察目标线与力矩改变，实际线仍留在原处。
2. 把实际角改到与目标相同，再把实际角速度设成正数：位置误差为零，阻尼项仍会产生负向力矩，帮助减速。

本例 `Kp=10 N·m/rad`、`Kd=1 N·m·s/rad`，输出限幅为 `±6 N·m`。目标 20°、实际 0°、速度 0 时为约 `+3.49 N·m`；目标与实际均为 20°、速度为 `+90°/s` 时为约 `−1.57 N·m`。

零 PD 输出只表示这个简化公式的结果，不代表真实机器人静止保持时不需要重力补偿或其他控制作用。

交互源文件归档在 [script/teaching/lesson01/policy-target-pd.html](../script/teaching/lesson01/policy-target-pd.html)，它是供聊天渲染的 HTML 片段；在浏览器中直接打开片段不能代表带主题的完整预览。

## 5. 训练在这个循环外增加评分与参数更新

训练的一轮可以先记成：

1. 策略在仿真里尝试控制机器人。
2. 环境返回新的观测和奖励，比如跟踪得好、保持平衡得到较好评分。
3. 收集一批这样的交互结果。
4. PPO 根据这些结果计算更新信号，通过反向传播调整网络参数。
5. 用更新后的策略继续尝试，另做评估。

奖励是任务评分，不是每一步“正确 action”的人工答案。更新希望提升累计奖励，并不保证每次更新都提升真实任务表现。

```python
# 控制/采集侧：在物理环境里积累交互
trajectory = collect_rollout(policy, simulator)

# 训练侧：PPO 根据这批经验构造损失，再修改参数
loss = compute_ppo_loss(trajectory)
optimizer.zero_grad()
loss.backward()
optimizer.step()
```

部署或普通评估通常保留策略前向计算与反馈控制，网络权重固定。机器人动作持续改变，也可以完全没有发生学习。
