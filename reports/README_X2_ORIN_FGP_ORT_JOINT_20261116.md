# X2 Orin FGP GPU 与 MorphMimic 线程联合对照

## Done

独立临时进程在 SoC1 用同一份 180 帧录制 IMU、原 S1 CUDA/TensorRT engine 和标定，按 4、2、2、4 个 MorphMimic ORT 线程的顺序进行四轮。每轮 FGP 都实际完成 GPU 推理、人体转换与 ZMQ 回环确认，预热后同样收到第 29–179 帧，共 151 帧。策略端用同一共享 REP、450 个按 50 Hz 计划的固定合成反馈请求。输入、engine 与标定运行前后 SHA-256 相同，逐就绪周期核对参考右支持未使用截止之后入库的帧。板端退出 0、预览锁释放。本次无 BLE、真实反馈或电机命令。

| 指标，两轮分别列出 | 4 线程 | 2 线程 |
| --- | ---: | ---: |
| FGP 单帧推理 P95 | 42.24 / 47.63 ms | 38.52 / 39.76 ms |
| FGP 出帧间隔 P95 | 53.77 / 57.57 ms | 46.18 / 47.51 ms |
| FGP 最长出帧间隔 | 68.06 / 76.25 ms | 52.30 / 60.43 ms |
| 状态 RPC P95 | 16.11 / 14.92 ms | 12.12 / 11.90 ms |
| 就绪状态超过 20 ms | 6 / 650 | 0 / 596 |
| 最大连续关节目标变化 | 15.54 / 15.54° | 17.21 / 15.58° |
| 录制计划释放至确认 P95 | 1439.63 / 1739.09 ms | 1036.75 / 1098.04 ms |

两个配置在首末就绪周期之间均未出现未就绪状态。这个连续就绪统计反映策略入库新鲜度，与录制计划释放点相比，参考仍可逐步积压。探针串行执行 FGP、转换、发送和等待确认，保留所有录制帧；这种积压是探针条件下的现象，不代表现有两帧在途流水线或真实 BLE 的端到端延迟。各轮时序和就绪窗口长度不同，动态策略目标并未做逐值等价验证。之前固定时钟下的 149 周期逐值一致仍单独成立。

2 线程在此联合负载下保留了状态期限收益，FGP 出帧也快了，仍未达到稳定 30 Hz。未切换现行入口。板端原件 `/tmp/x2-ort-fgp-joint.YEyV6q/run/result.json` 已与 Mac 核同 SHA-256。
